# 八字排盘产品化与商业扩展架构规划

> 版本：产品规划草案 v1.0  
> 日期：2026-11-03  
> 对应仓库：`bbaa2023/bazi-paipan`  
> 状态：规划阶段，尚未实施收费、账号、后端或 AI 接口

## 1. 本文的目的

本项目从一开始就按可持续扩展的产品设计，而不是一次性排盘页面。当前阶段优先完善功能清单、领域边界、数据契约和未来扩展点；不急于改页面，也不提前接入支付、模型或人工服务。

长期产品目标：

- 免费排盘作为流量入口，提供完整、可信、可分享的基础排盘资料。
- 通过更深入的专题分析和报告，提供低门槛付费服务。
- 通过多轮 AI 深度解读，提供更高阶的个性化服务。
- 通过人工复核、咨询或定制分析，承接高价值需求。
- 增加合盘等多对象分析能力，同时保持单人本命排盘稳定。

核心原则：**免费排盘、命理分析、AI 服务、订单会员、人工服务是不同业务层，不要耦合成一个页面或一个巨大函数。**

## 2. 产品服务梯度

| 层级 | 产品形态 | 主要交付 | 当前状态 |
|---|---|---|---|
| L0 免费体验 | 免费排盘 | 完整四柱、基础五行、十神、藏干、纳音、大运流年基础资料、部分关系资料 | 当前产品建设重点 |
| L1 轻量付费 | 专题简析/单项报告 | 例如事业、财务倾向、关系、阶段运势等专题；由固定分析流程生成结构化结果 | 仅规划 |
| L2 AI 深度解读 | 完整命盘解读 | 多维资料综合、用户问题上下文、分章节报告、追问与补充分析 | 仅规划 |
| L3 高阶服务 | 人工复核/人工咨询 | AI 初稿辅助 + 人工审核、定制解读或咨询服务 | 仅规划 |
| L4 多人关系产品 | 合盘/关系分析 | 两人或多人命盘对照、关系结构、双方时间维度分析 | 仅规划 |

层级不是简单地把免费内容删掉再收费。免费版仍应有完整排盘数据；收费价值来自更深的综合分析、个性化问题、报告质量、持续服务和人工投入。

不得把传统命理结论包装成确定性的人生、医疗、投资或法律保证。付费内容同样要说明分析依据、流派口径和不确定性。

## 3. 领域分层与模块边界

建议未来逻辑分为以下领域层。当前可以继续由静态页面承载，但代码和数据契约要按这些边界组织。

### 3.1 排盘核心（Chart Domain）

职责：根据出生资料计算标准化命盘，不承担营销、支付或 AI 文案。

输入契约建议包含：
- 出生日期、时分；未知时辰标记
- 性别（仅在对应算法确实需要时使用）
- 时区偏移、时区标识（未来可扩展）
- 出生地经度、中央经线
- 真太阳时/民用时口径
- 换日流派/子时口径
- 排盘引擎版本与规则版本

输出建议包装为版本化的 `ChartSnapshot`：
- `schemaVersion`：数据结构版本
- `engineVersion`：引擎版本
- `createdAt`：生成时间
- `birthInput`：规范化后的输入摘要
- `calculationOptions`：时区、真太阳时、换日、起运等口径
- `pillars`：四柱及其原始引擎字段
- `meta`：日主、节气边界、时差修正等元信息
- `derivedProfiles`：日柱、地支、十神、十二长生等派生剖面
- `sourceTrace`：各字段来源接口/版本，便于复核

这是一层包装契约，不要求现在改变引擎原始返回对象。应保留原始结果，避免数据丢失；新结构可逐步映射。

### 3.2 命理分析（Analysis Domain）

职责：把排盘事实转成可解释的分析，不直接负责收费和模型供应商。

分析输入：
- 一个或多个 ChartSnapshot
- 分析主题（事业、财务、关系、家庭、阶段运势等）
- 分析时间范围（本命、大运、流年、指定年份）
- 用户提出的问题（可选）
- 分析规则/知识库版本

分析输出建议采用结构化 `AnalysisResult`：
- `analysisId`、`schemaVersion`
- `chartRefs`：所使用的命盘快照及版本
- `topic`、`timeScope`
- `evidence[]`：参与判断的柱位、干支、十神、五行、关系、时间边界
- `findings[]`：观察点、解释、倾向、限制条件
- `uncertainties[]`：缺失时辰、边界时间、流派差异等
- `summary`、`sections[]`、`followUpQuestions[]`
- `promptVersion`、`knowledgeVersion`、`modelInfo`（使用 AI 时填写）

分析必须能追溯到命盘证据。模型不应自行重新排盘或擅自改写计算结果；排盘以本地引擎的标准化快照为准。

### 3.3 AI 服务适配层（AI Provider Adapter）

未来 AI 分析不能直接散落在页面按钮中，也不能把模型 API Key 放在浏览器。

建议抽象为统一调用接口：
- `analyzeChart(request)`
- `continueAnalysis(analysisId, message)`
- `generateReport(analysisId, format)`
- `estimateCost(request)`（可选）
- `getTaskStatus(taskId)`（异步任务）

模型供应商通过 Adapter 接入，可更换不同云模型或本地模型；业务流程不直接依赖某一家模型。模型名称、价格、上下文长度和可用性属于配置，不写死在前端。

提示词应模板化、版本化、按主题拆分，并记录版本；不要把所有命理规则堆在一个超长提示词中。模型输出需做结构校验、敏感内容检查和证据一致性检查。

### 3.4 会员、订单与权益（Commerce Domain）

未来独立处理：
- 用户身份与登录态
- 商品/SKU 与服务层级
- 订单、支付状态、退款状态
- 权益发放、消耗、到期
- AI 调用额度/报告次数
- 人工服务预约与交付状态

排盘页面只展示可购买的服务并发起业务请求；不能自己判断“用户已付费”。权益必须由服务端订单记录确认，模型调用前再次校验权益与额度。

建议预留业务对象：
- `ProductPlan`：商品和服务定义
- `Order`：订单及支付状态
- `Entitlement`：用户拥有的权益
- `UsageRecord`：模型调用、报告生成、额度扣减记录
- `ServiceCase`：人工服务工单与交付记录

支付渠道、用户系统、数据存储位置和实际部署拓扑待单独评审，不在当前静态排盘站里临时拼装。

### 3.5 合盘与多人关系（Compatibility Domain）

合盘不是把两人的八字字段简单拼接，也不应该改造单人排盘接口。

建议：
- 每个人分别生成独立 `ChartSnapshot`。
- 合盘模块接收 `chartRefs[]`，至少两份快照。
- 独立输出 `CompatibilityResult`，记录双方命盘版本、参与柱位、关系证据、时间维度和分析口径。
- 支持双方本命关系、大运阶段交互、指定年份/流年关系。
- 未知时辰时明确标记结果范围，不补造时柱。
- 将传统关系规则与 AI 综合解释分开保存。

这样未来可支持伴侣合盘、亲子关系、合作关系等场景，而不会污染单人排盘核心。

### 3.6 人工服务（Human Service Domain）

AI 报告和人工服务是两个独立交付：
- 用户授权后才提交给人工服务。
- 服务工单记录用户问题、命盘快照引用、已购买项目、交付状态。
- 人工修改/复核意见与 AI 原始结果分开保存。
- 需要支持撤回、删除、访问控制和操作记录。

## 4. 建议预留的 API 边界

以下是未来逻辑接口的建议命名，不代表现在已经存在或可以调用：

| 接口边界 | 示例接口 | 负责内容 |
|---|---|---|
| 排盘 | `POST /api/v1/charts` | 创建单人命盘快照 |
| 查询排盘 | `GET /api/v1/charts/{chartId}` | 读取命盘及计算口径 |
| 合盘 | `POST /api/v1/compatibility` | 两份或多份命盘对照 |
| 分析任务 | `POST /api/v1/analysis-tasks` | 创建专题/深度 AI 分析 |
| 任务状态 | `GET /api/v1/analysis-tasks/{taskId}` | 查询异步生成状态 |
| 分析结果 | `GET /api/v1/analyses/{analysisId}` | 获取结构化解读 |
| 报告 | `POST /api/v1/reports` | 生成可下载/可分享报告 |
| 商品 | `GET /api/v1/products` | 获取可购买服务 |
| 订单 | `POST /api/v1/orders` | 创建订单 |
| 权益 | `GET /api/v1/entitlements` | 查询会员权益/可用次数 |
| 人工服务 | `POST /api/v1/service-cases` | 提交人工服务申请 |

当前免费静态排盘可继续在浏览器本地运行，不需要为了预留这些路径而提前建设后端。未来新增后端时，页面通过独立 API Client 调用，不直接依赖数据库或模型供应商。

## 5. 前后端解耦与扩展规则

1. **引擎适配器**：前端业务模块不直接到处调用 vendor 全局对象；未来逐步通过统一 Engine Adapter 访问，原始引擎 API 保持原样。
2. **数据契约版本化**：ChartSnapshot、AnalysisResult、CompatibilityResult 均带 schemaVersion；引擎升级时建立映射和回归测试。
3. **业务服务接口化**：页面只调用 ChartService、AnalysisService、CommerceService、CompatibilityService 等逻辑入口。
4. **AI 供应商隔离**：模型供应商切换不影响分析结果结构、订单权益和页面。
5. **异步任务预留**：深度报告可能耗时，预留 taskId、状态查询、失败重试和幂等键。
6. **权限服务端校验**：任何收费内容、模型调用和人工服务提交都必须服务端校验登录、订单和权益。
7. **原始证据保留**：报告记录使用的命盘快照、计算口径、提示词版本、知识版本和模型信息。
8. **不破坏免费链路**：免费排盘不能依赖付费服务或 AI 才能完成；付费服务故障不应影响基础排盘。
9. **兼容旧数据**：接口新增字段优先可选；需要破坏性变更时提升 schemaVersion 并提供迁移。
10. **不把密钥放前端**：支付密钥、模型密钥、数据库凭证只能留在受控服务端。

## 6. 隐私、安全与数据治理

出生日期、时间、地点以及由此生成的命盘属于用户个人资料，应按最小必要原则处理。

- 免费本地排盘优先在浏览器本地完成；除非用户主动保存/同步，不默认上传出生资料。
- 发送给 AI、人工服务或第三方前，明确告知数据用途并取得用户主动授权。
- 对外部模型只发送当前分析必需的数据；能用命盘结构摘要解决的，不发送无关身份资料。
- 用户可查看、导出、删除其保存的命盘和分析记录；删除策略应覆盖备份与服务商保留规则。
- 会员、订单和命盘数据应有清晰访问边界；运营人员不应默认读取完整命盘内容。
- 日志不记录模型密钥、支付凭证或不必要的出生个人信息。
- 数据托管位置、跨境传输、支付合规和隐私政策需在正式收费前单独评估。

## 7. 现阶段不做的事情

在产品功能和数据契约确认之前，暂不：
- 接入支付、会员登录或付费墙。
- 接入豆包或任何单一模型供应商。
- 把模型提示词写进前端并暴露密钥。
- 把 AI 解读逻辑塞进排盘引擎。
- 把合盘逻辑塞进 `computeBazi`。
- 将用户命盘默认上传到 VPS2 或任何第三方。
- 为了收费而删减免费排盘的核心资料。
- 重写当前页面或更换排盘引擎。

## 8. 产品规划实施顺序

### P0：产品功能与数据资产盘点
完成引擎 API 审计、现有功能审计、数据来源表、模块地图和术语规范。当前正在进行。

### P1：单人排盘完整产品定义
完成本命、日柱、地支、十神、五行、关系、大运、流年、太岁、神煞、空亡、传统资料库的功能规格和相互链接规则。

### P2：多对象分析与合盘规格
定义多命盘输入、关系证据模型、双方时间轴、未知时辰边界和结果结构；先出规格与测试样例，不急着开发。

### P3：AI 解读产品规格
定义专题商品、报告章节、证据引用、提示词版本、模型适配、成本估算、任务状态、质量检查与人工复核边界。

### P4：商业化服务规格
定义账号、订单、支付、权益、额度、退款、人工工单和隐私授权流程。先选业务方案，再确定服务端部署位置。

### P5：逐项实施
按用户真实需求和阶段收益逐项实施，每项先做设计、测试和备份；不进行无计划的大重构。

## 9. 当前决策记录

- 当前先做产品规划和功能完善，不急于修改页面。
- 现有本地排盘引擎作为单人排盘计算核心，暂不替换。
- 免费排盘保持本地可用，不依赖 AI 或 VPS2。
- 合盘、AI 解读、会员订单、报告生成、人工服务属于未来独立业务域。
- 现在只预留清晰的数据契约和服务边界，不提前启用外部服务。
- 后续每个阶段需单独审计、备份、提交和验收；未经确认不改变现有计算口径。


## 10. 独立知识库（新增产品区域，2026-11-03）

免费排盘之外增加独立的“八字知识库”一级区域。它是公开资料与知识学习模块，不属于命盘计算引擎，也不是排盘页中的教学面板。

- 排盘页面继续作为核心工具；页面说明只承担轻量导航，提示功能用途、相关联资料和查看入口。
- 知识库独立组织首页、分类页和文章页，围绕排盘实际功能建设基础知识、天干地支、十神、藏干、十二长生、干支关系、大运流年、神煞和排盘规则等内容。
- 排盘页与知识库双向链接，但知识库不读取当前命盘、不接收出生资料。
- 内容来源分层：本站引擎实现、经典文献、流派观点、现代整理资料分别标注；没有可核验出处的内容不作为确定规则发布。
- 首期采用静态页面，不引入数据库、账号、支付、AI 或后端服务；不修改本地排盘引擎。
- 详细规范见 `docs/KNOWLEDGE_BASE_INFORMATION_ARCHITECTURE.md`。

实施顺序调整为：先完成知识库信息架构，再建设独立静态框架，随后为现有排盘功能增加简短导航入口，最后逐步整理首批知识条目。此模块不改变 L0 免费排盘的计算范围，也不启用 L1-L4 商业服务。


## 11. 大运分析的长期研究方向（专业服务）

长期专业分析以《渊海子平》《滴天髓阐微》《三命通会》等为理论研究来源，需要综合月令、旺衰、格局、用神、调候、通关、根气、制化、刑冲合会及大运对原局的实际作用。该范围不属于当前 L0 免费版。

- 专业规则必须先完成专项研究、命例验证和证据规范，再进入产品实现。
- 不把简化扶抑模型、两两关系接口或单项神煞当成完整断运能力。
- 详细的免费版与专业版边界见第 12 节及 `docs/DA_YUN_JUDGEMENT_RULES.md`。


## 12. 免费版基础大运趋势与专业分析边界（2026-11-03）

此前第 11 节所列的完整命局综合判断流程，现明确归入未来专业付费分析规划，不属于 L0 免费版交付范围。L0 仅建设“基础大运趋势”提示。

### 12.1 L0 免费版

- 只使用现有排盘事实和引擎已有的简化扶抑参考。
- 初步只比较大运天干五行、地支主气五行与简化扶抑方向是否一致。
- 结果限于“基础偏有利、基础偏谨慎、因素交错、暂不判断”四种状态。
- 大运十神、藏干、十二长生和关系资料继续作为排盘信息展示，不单独推导吉凶。
- 不分析月令司令、综合旺衰、格局、完整用神、调候、通关、刑冲合会实际作用、合化及大运流年综合影响。
- 详细规则见 `docs/DA_YUN_JUDGEMENT_RULES.md`。

### 12.2 L1/L2 未来专业分析

月令、旺衰、格局、用神、调候、通关、根气、制化、刑冲合会及大运对原局的实际作用，统一纳入未来专业付费分析规则体系。需要分模块研究、建立可核验命例和准确性测试，不能因商业需求而提前简化成未经验证的自动断语。

### 12.3 架构约束

- 免费趋势模块与未来专业分析模块逻辑隔离，不能把免费标签当作专业分析结论复用。
- 免费版不向 VPS2 或第三方发送出生资料，不调用付费模型或专业服务。
- 未来专业分析以版本化命盘快照为输入，记录规则、知识库、引擎版本和证据来源。
- 免责声明应明确免费版仅使用简化规则；未来付费分析同样不作现实结果保证。
- 基础趋势卡片已提交 main，接入现有简化扶抑参考与大运干支五行；vendor 引擎未修改。静态检查、命例验证、真实浏览器验收和 VPS1 部署仍未完成。
