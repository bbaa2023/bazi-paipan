## 1. 产品定位

本站由两个相互关联、职责分离的一级区域组成：

1. **免费八字排盘**：核心工具。负责出生资料输入、命盘计算、资料展示、时间轴选择和关系定位。
2. **八字知识库**：独立辅助区域。负责概念查询、排盘规则说明、分类资料和知识学习。

排盘页面不是教学页面。知识库也不承担命盘计算或个性化断命。两者通过统一的功能名称、简短说明和双向链接连接。

## 2. 排盘页面导航规范

排盘页面的说明只回答三个问题：

- 这是什么功能？
- 它与命盘的哪些部分或其他功能有关？
- 用户应该在哪里查看相关资料？

### 2.1 文案尺度

- 每项功能通常一至两句话，优先一句话。
- 使用普通用户能理解的表达，不在主页面展开理论、推导或古籍长文。
- 说明功能之间的关联，但不把相关性说成因果或吉凶判断。
- 只在有对应知识条目时显示“了解更多”链接；链接应准确落到相关条目，不使用无目标的装饰链接。
- 说明采用轻量视觉层级，不占用命盘主要展示空间，不重复解释页面上已经清楚显示的字段。
- 未知时辰、未选择性别、引擎没有返回数据等边界提示仍应保留，它们属于正确使用工具所必需的信息，不应被当作教学文字删除。

## 4. 页面与文件结构建议

知识库作为现有静态站点中的独立页面区域，首期不引入后端、数据库、框架或 Docker。

首期实际采用轻量静态结构：

```text
guide/
├── index.html                 # 知识库首页与分类搜索
├── category.html              # 分类页模板，通过 ?topic= 分类 ID 读取目录
└── assets/
    ├── guide.css              # 独立样式
    └── guide.js               # 分类目录、搜索与页面渲染
```

这种方式先减少重复页面和维护成本。后续文章数量、SEO 和独立收录需求明确后，再将重要分类与文章拆成独立目录/HTML 页面；不为了形式提前创建大量空文件。

主排盘页面通过顶栏“知识库”入口进入 `./guide/`。知识库页面提供“返回排盘”入口。文章内的排盘关联链接应指向真实存在的排盘功能或页面锚点；当前排盘结果依赖用户本地输入，知识库不读取、不上传用户出生资料。

## 5. 知识条目模板与来源规范

每篇知识条目建议包含：

1. 标题与一句话摘要。
2. 基本概念：简明说明是什么。
3. 规则/资料：用表格或短列表呈现必要内容。
4. 排盘中的位置：告诉用户在排盘页面哪里能看到。
5. 相关条目：提供上下游知识链接。
6. 来源与口径：说明使用的引擎规则、经典文献版本/篇目，或现代整理资料。

来源类型必须明确区分：

- **本站引擎规则**：对应实际随仓库发布的引擎实现或规则表；不得冒充古籍原文。
- **经典文献**：必须记录书名、版本/整理本、篇目或章节；引用原文时应可核验。
- **流派观点**：标注具体差异，不把有争议的名称或规则写成唯一标准。
- **现代整理资料**：记录作者/出版信息或可靠来源，并与引擎实际计算口径区分。

如果暂时找不到可靠出处，应标记“来源待核验”并暂不发布为确定规则。不得为了让知识库看起来完整而补造古籍出处、原文或规则解释。

## 6. 搜索与发现

知识库达到一定条目数量后提供站内搜索。首期可采用静态文章索引和浏览器端检索，不上传用户搜索内容或出生资料。

搜索范围至少包括标题、摘要、分类和关键词。搜索结果需链接到具体文章，不只返回分类首页。

## 7. 视觉与交互原则

- 延续本站现有的宣纸、深蓝文字和金色点缀视觉体系，但知识库采用更适合阅读的内容版式。
- 桌面端可使用左侧分类导航、右侧文章内容；手机端改为顶部分类入口或可折叠目录。
- 标题、摘要、正文层级清晰，表格在窄屏可横向滚动或转换为卡片。
- 排盘页面只使用小型说明、问号/资料链接等轻量组件，不新增大型教学面板。
- 知识库不使用弹窗强迫阅读，不阻断排盘流程。

## 8. 隐私与技术边界

- 知识库是静态公开资料，不接收命盘或出生资料。
- 排盘计算继续在用户浏览器本地完成。
- 不将出生资料、命盘结果或用户输入发送到知识库搜索、统计或第三方服务。
- 不修改 `vendor/lunar.js` 或 `vendor/bazi-engine.web.js`。
- 不引入支付、会员、AI 调用、用户账户或后端 API。
- 知识库内容版本与排盘引擎版本分别记录；引擎规则更新时检查受影响的知识条目。

## 16. 神煞剩余条目规则与古籍口径审计（2026-11-03）

本节为内部资料，不直接展示给知识库访客。目标是避免把引擎当前扫描表误写成某一部古籍的唯一传统规则。

### 文昌

- 引擎当前 SS_WENCHANG 按日干索引的表为：甲巳、乙午、丙申、丁酉、戊申、己酉、庚亥、辛子、壬寅、癸卯；扫描锚点为日干，检查四柱地支。
- 《三命通会》卷三“论太极贵”同段列出的“文昌贵”口诀却是：甲巳、乙亥、丙戌、丁辰、戊申、己午、庚寅、辛未、壬卯、癸丑；该篇还并列文誉贵、文星贵，不能混为一表。
- 《命理探源》“文昌”条及相关现代整理资料记录了与引擎表一致的通行查法，并以日干食神的临官/长生位置解释其推导；但其底本与《三命通会》卷三的“文昌贵”歌诀并非同一口径。
- 处理结论：可以另写“本站采用的通行文昌查法”专题，但必须明确引擎采用通行表，不得引用《三命通会》卷三那首不同口诀作为直接依据。若不能把《命理探源》底本版本与篇目稳定链接，先不发布。

### 福星贵人

- 引擎当前 SS_FUXING 是日干索引到地支集合的查表；扫描器仅按日干确定目标支，再检查四柱地支是否命中。它没有在扫描阶段校验被命中的柱干支组合，也没有执行本旬“真食神”遁法。
- 《三命通会》卷六“福星贵人”原文以甲人见丙寅、丙子，乙人见丁亥、丁丑为例，说明“遁得本旬中真食神”；并特别指出前人歌诀以年论，若以日遁则不同。
- 因此不能简单说“引擎日干查表与古籍年干查法不同”就结束；关键差异是引擎按日干+地支命中，而古籍示例包含完整干支与旬内遁法。两者的判定条件不同。
- 处理结论：暂不新增古籍依据专题。若未来要保留现有引擎输出，应命名为“本站福星查表口径”，并明确它是当前程序规则表，不宣称完整复现《三命通会》卷六的本旬真食神法。

### 国印贵人

- 引擎当前 SS_GUOYIN 表为：甲戌、乙亥、丙丑、丁寅、戊丑、己寅、庚辰、辛巳、壬未、癸申；扫描锚点为日干，检查四柱地支。
- 本轮检索到的现代资料多以相同或近似表格传播，但尚未定位到可稳定核验、明确记载该十干表及其起例锚点的古籍原文。
- 处理结论：继续暂缓专题。不能只因多个现代网站表格相同，就推定其为《三命通会》或《渊海子平》的原文规则。

### 后续准入标准

1. 先记录引擎真实表、扫描锚点、比较字段（只看支或看完整干支）和未知时辰处理。
2. 再找到可定位的古籍版本、卷篇及对应原文；同名异法必须分列。
3. 如果只能确认引擎规则，文章应标为“本站当前查表口径”，不得伪装成古籍定法。
4. 暂时没有充分出处时，保留分类索引但不发布专题文章。
5. 不修改 vendor 算法；如发现引擎扫描条件与其规则注释不一致，单独登记为引擎准确性审查事项，不在知识库文案中掩盖。
